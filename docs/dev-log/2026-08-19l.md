# 2026-08-19 (session 12)

## Session — Phase B: roles + patient portal auth

**Goal**

Second of 5 phases in the landing/icon/portal/scheduling plan. Adds
`User.role`/`patient_id`, a clinician-issued invite/claim flow (no patient
self-registration), the `require_clinician`/`require_patient`/
`current_patient_record` dependencies, and a minimal `portal.py` router
for a patient's own chart. This is the hard prerequisite the plan flagged:
scheduling/results sharing (Phase C) and the frontend split (Phase D) both
assume roles exist.

**Did**

- Model: `User.role` (`server_default="clinician"` — the backfill for
  every existing row, no data migration step needed), `User.patient_id`
  (nullable, unique FK), a `CheckConstraint` forbidding a patient role
  with no bound chart. New `PatientInvite` table.
- Generated the Alembic migration against a real local Postgres
  (`docker compose up -d postgres`), applied it, downgraded it, and
  re-applied it to prove both directions work before trusting the drift
  guard. Autogenerate got almost everything right this time (even the
  `CheckConstraint`, via the `checkconstraint_byname` plugin) — the one
  hand-fix was naming `users.patient_id`'s FK explicitly in both
  directions, since `op.drop_constraint(None, ...)` isn't droppable by
  name and `downgrade()` would have failed silently until someone tried
  it.
- `auth/deps.py`: `require_clinician`, `require_patient`,
  `current_patient_record` (patient derived from the token only),
  `require_clinician_for_registration` (the bootstrap-flag gate on
  `POST /api/auth/register`).
- `auth/router.py`: `register` becomes clinician-only;
  `RegisterRequest`/`ClaimInviteRequest` both `extra="forbid"` so `role`/
  `patient_id` can never be smuggled in; new `POST /api/auth/portal/claim`
  redeems an invite — every failure mode returns the identical generic
  400 so the endpoint can't be used to enumerate invite ids.
- `patients.py`: new `POST /api/patients/{id}/invites` — composite code
  `"{invite_id}.{secret}"`, secret hashed at rest, returned once.
- New `portal.py`: `GET /api/portal/{me,timeline,labs}`, all keyed off
  `current_patient_record`, never a path/query id. Deliberately not
  `patients.py::_full` — no `risk_level`/`risk_flags` (clinician-facing,
  rule-derived), timeline filtered to non-AI-generated events.
- `main.py`: swapped Phase A's `get_current_user` placeholder for the
  real `require_clinician` on the five clinician-only routers, plus wired
  the new `portal` router (no blanket guard — mixes roles per-route).

**Decisions**

- **Portal derives identity from the token only, never a parameter.**
  `current_patient_record` is the one entrypoint; no portal handler
  accepts `patient_id`, so there's no id for a caller to tamper with.
  Verified by a route-shape meta-test, not just example-based tests.
- **No patient self-registration, full stop.** Identity proofing (is this
  person actually the patient named on this chart?) is a human, in-clinic
  step. The system accepts an identity assertion only from someone
  already trusted — a clinician issuing an invite — never from form
  fields a caller controls.
- **Role stays out of the JWT.** Re-read from the DB every request so a
  role change (or, later, deactivation) takes effect immediately rather
  than surviving until token expiry.

**Tried and rejected**

- Nothing structural — the design (from the earlier planning pass) held
  up during implementation. The only real surprise was how clean the
  autogenerated migration came out compared to Phase 5's telemetry/
  recovery migrations, which needed more hand-fixing.

**Problems**

- One test needed updating (`test_update_profile`'s exact-set assertion

- Chased 100% line coverage on `auth/deps.py`'s pre-existing
  `get_current_user` "user no longer exists" branch briefly, then
  stopped — it predates this phase and isn't part of what Phase B is
  responsible for proving; the global 87% gate (actual: 93%) was never
  at risk.
