# 2026-08-19 (session 3)

## Session — Phase 4b: Verification & Safety

**Goal**

Implement `SPEC-004`: claim-level content verification (replacing the
assumption that citation-provenance checking alone was enough) and an
abstention gate (the largest documented gap per
`docs/06-security/safety.md`). Scoped to Verification & Safety only (Phase
4b) — Context Engine (4a: reranking, memory, compression, token budgeting)
is a separate, not-yet-written spec.

**Decisions**

- **`citation_guard.py` is not shimmed this phase**, despite the charter's
  original schedule calling for it. It becomes a pre-filter feeding the new
  verifier (ADR-006's own framing) — real, unmodified, still useful in
  production. Shimming/deleting it is deferred until the new verifier has
  demonstrably absorbed its role, not assumed complete on day one.
- **`verify_claims` batches all claims into one `generate_json` call**, not
  one call per claim, to keep ADR-006's dominant cost at O(1) round-trips.
  Mitigated the "the judge can be wrong" risk with a cheap deterministic
  token-overlap downgrade rule rather than trusting the judge alone.
- **`risk_level` (coarse per-consultation risk) does not gate abstention** —
  only claim-level risk does, per the spec's stated invariant
  (`has_unsupported_high_risk_claim`). A plausible alternative (always
  abstain on `CRITICAL` risk_level) was deliberately rejected.
- **Output safety scope cut to exactly one thing**: an input prompt-injection
  heuristic wired to `POLICY_RESTRICTION`. PHI redaction of clinical text is
  out of scope — the product exists to show a clinician their own patient's
  data, so redacting it would break the product itself.

**Tried and rejected**

- An earlier draft of `test_run_consultation_abstains_on_unsupported_high_risk_claim`
  tried to script the abstain scenario purely through `FakeLLMClient.json_payloads`,
  matching a verdict's `claim_id` against a hardcoded placeholder string —
  but claim ids are `uuid4().hex`-generated inside `extract_claims`, unknown
  to the test in advance. Rewrote it to monkeypatch
  `extract_claims`/`verify_claims` directly, since the extraction/verification
  logic itself is already unit-tested elsewhere.

**Problems**

- **The design agent's first draft flagged a "router cutover" as required
  scope** — the belief that `platform/api/routers/agents.py` still imported
  the old `intelligence.agents.workflow` graph, not the Phase 3 executor.
  Verified directly: it *is* already the executor, via the shim's proven
  identity (`test_agent_registry.py::test_workflow_shim_run_consultation_is_the_real_executor`
  from Phase 3). No cutover needed — corrected before writing the plan.
- **`test_final_event_shape`'s exact-set assertion broke**, as expected —
  the two new additive keys grew the set. Fixed with the same one-line
  "additive, documented" pattern used in every prior phase's frozen-file
  touch.
- **`docs_check.py`'s AC-coverage gate failed for all 9 new criteria** until
  each got a one-line docstring anchor in its test file — same pattern as
  every prior phase.
- **Ruff's markdown-embedded-code formatting** flagged two Python code
  fences inside `SPEC-004-verification-safety.md` itself (interface stub
  signatures too long) — reformatted them to match `ruff format`'s
  line-wrapping, since the gate checks `.md` code blocks too.
- **Autogenerate's migration was unsafe by default**: `NOT NULL` columns
  with no `server_default` would fail against any pre-existing row (e.g.
  Supabase's live data). Added `server_default='{}'` by hand, then verified
  by actually applying the migration to a fresh local Postgres and running
  `tests/test_alembic_migration.py` (the drift guard) against it — passed,
  confirming the model and the migration agree.
