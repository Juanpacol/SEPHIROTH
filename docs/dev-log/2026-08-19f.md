## Session — Phase 5, Part 1: Telemetry (trace-based observability)

**Goal**

First of 5 planned cycles closing the remaining SEPHIROTH gaps. Executes
`ADR-009`: every consultation now builds and persists a structured,
replayable `ExecutionTrace` — the contract has existed since Phase 0,
fully tested, with nothing emitting into it until this session.

**Did**

- Read the existing contracts fully before designing anything:
  `ExecutionTrace`/`Span`/`TokenUsage` (`sephiroth.contracts.trace`),
  `RunState`, `ExecutionPlan`/`PlanStep` bounds, `ADR-009`'s full text —
  confirmed the redaction allow-list is already enforced at `Span`
  construction, and nothing needed rediscovering there.
- Built `src/sephiroth/telemetry/{span,build_trace}.py`. Deliberately
  scoped down from the original plan's 4-seam design (which sketched a
  pluggable `Tracer`/`SpanHandle` Protocol with an `OTelTracer` option) to
  something much simpler once I traced the actual call graph: `Agent.run()`
  makes exactly one `chat()` call per turn, so a span around the executor's
  per-agent call already bounds the model interaction as tightly as a
  separate nested span would — no need for a Protocol or a second
  instrumentation point there. Threading a per-request state object into
  `ToolRuntime.execute()` (a shared singleton) would have changed
  `ToolExecutor`'s `Callable` signature that `FakeLLMClient` and every
  `scoped_executor()` call site depend on — a real API break for a nice
  overlap, not a documented tradeoff. Cut both from this cycle's scope,
  documented as `SPEC-006` NG-1.
- Wired `traced_span` into `_run_specialist`, both coordinator call sites,
  and `_verify_and_decide` in `src/sephiroth/runtime/executor.py`.
- Added `RunState.spans`, `enable_tracing` setting, `trace` as an additive
  key on `run_consultation`/`stream_consultation` and the `final` SSE
  event, 5 new nullable `Consultation` columns + migration.
- Wrote `docs/specs/SPEC-006-telemetry.md`, updated `feature-registry.md`
  (F-042/F-043), `traceability.md` (R-006), `project-state.yaml`.

**Decisions**

- **No pluggable Tracer/OTel Protocol this cycle** (NG-3) — `ADR-009`
  allows one, but building the abstraction with a single consumer (one
  Postgres JSON column) and no second backend to swap to is exactly the
  premature complexity this project has avoided at every prior phase.
  `opentelemetry-api` sits in `.venv` as a transitive dependency, unwired.
- **Token/cost fields stay at 0** (NG-2) — real numbers need
  `GeminiClient`/`GroqClient` to report usage metadata, a separate, later
  change to the model clients themselves, not something to fake here.

**Tried and rejected**

- The plan's original `Tracer`/`SpanHandle` Protocol design — abandoned
  after tracing the actual call graph showed it would either duplicate the
  `Executor.step` span (for `ModelProvider.chat`) or require an API-breaking
  change to `ToolExecutor`'s signature (for `ToolRuntime.execute`). Simpler,
  more honest to scope down and document than to build unused abstraction.

**Problems**

- **`VerificationReport.supported_claim_ratio` is a Pydantic `@property`,
  not a `computed_field`** — doesn't survive `model_dump()`. Caught before
  writing `_persist`'s logic (traced through what `model_dump(mode="json")`
  actually produces rather than assuming), fixed by recomputing the ratio
  directly from the already-serialized `verification_report`'s claim
  `status` values instead of reading a field that would have silently
  always been `None`. Documented in `SPEC-006` §10 as friction found during
  implementation, not silently patched over.
- **`test_final_event_shape`'s exact-set assertion broke**, as expected —
  the additive `trace` key grew the set. Same one-line "additive,
  documented" pattern as every prior phase's frozen-file touch.
- **`docs_check.py`'s AC-coverage gate failed for all 7 new criteria**
  until each got a one-line docstring anchor — same pattern as every prior
  phase.
