## Session 1 — Phase 1: ModelProvider

**Goal**

Implement `SPEC-001` end to end: a formal `ModelProvider` Protocol, Gemini and
Groq retrofitted behind it, config-driven provider selection — with zero
change to default behavior.

**Did**

- Wrote the three SPEC-001 test files first (`test_model_provider_protocol.py`,
  `test_throttle.py`, `test_llm_shims.py`) and confirmed they failed against
  nonexistent code before writing any implementation.
- Built `src/sephiroth/models/{base,_throttle,gemini,groq,fallback,factory}.py`.
  Extracted `RateLimiter`/`backoff_delay` from `GeminiClient`'s previously
  duplicated retry logic; `describe_image` now reuses `_generate` instead of
  carrying its own copy.
- Added `llm_provider`/`groq_timeout_seconds`/`groq_max_output_tokens`/
  `groq_rpm_limit` to `Settings`, all defaulting to current behavior.
- Turned `intelligence/llm/*` into re-export shims.
- Retargeted `conftest.py::patch_llm_factory` to `sephiroth.models.factory`.

**Decisions**

- **AC-001-02/03 verify the Protocol's own signature, not each
  implementation's.** The three concrete clients keep their exact current
  signatures — zero risk, zero behavior change. The Protocol is the contract;
  every call site already uses it correctly by convention.
- **`llm_provider="groq"` returns a bare `GroqClient`**, not a fallback
  wrapper the other direction. Groq has no vision endpoint, so a symmetric
  fallback would tangle `describe_image` semantics for no acceptance
  criterion that needs it.

**Tried and rejected**

- Nothing structural — this phase followed the plan closely. The one thing
  that changed mid-implementation was scope, not approach (see below).

**Problems**

- **The factory-global trap was broader than `SPEC-001` §10 described.**
  While fixing `test_llm_factory.py` I found the identical pattern in
  `test_api_agents.py` and `test_api_patients_rag.py` — both build local `app`
  fixtures that patch `intelligence.llm.factory`'s module globals directly.
  Running the full suite caught this immediately: 17 tests errored with
  `AttributeError: module ... has no attribute '_client'`, because the shim
  doesn't define its own `_client` — it re-exports functions, not the mutable
  global those functions close over. Fixed by retargeting all three test
  files' `factory_module` import to `sephiroth.models.factory` (two lines
  each), and corrected `SPEC-001` §10 with the fuller list.
- `ruff format` wanted a one-line collapse in a new test file; harmless, fixed.

**Results**

- 359 → **392 tests**, all green. Coverage **91.05% → 92.01%**.
- The four legacy LLM test modules pass with zero behavioral change.
- Eval gate: PASS on all six metrics, unchanged.
- `docs_check`: 0 warnings — all 10 `AC-001-*` are now discoverable in the
  test tree (three one-line comments added to legacy test files, anchoring
  AC-001-04/05/06 without touching any assertion).
- `SPEC-001` → `Implemented` (v1.1.0).

**Next**

- Phase 2 per the migration charter: Tool Runtime. Same order — spec is
  already `Approved`-eligible reading, write its ACs as failing tests first.

## Session 2 — Fixing a broken commit: `.gitignore` silently dropped `src/sephiroth/models/`

**Goal**

Start Phase 2 by branching from `phase-1-model-provider`.

**Problem**

Branching found the bug: `git checkout main && git checkout -b phase-2-tool-runtime`
left `phase-2` pointed at pre-Phase-0 `main`, and `git status` came back clean
even though `src/sephiroth/models/*.py` were sitting right there on disk. That
was the tell. `git check-ignore` found it immediately: a pre-existing
`.gitignore` rule —

```
# Models (large binaries)
models/
```

— written for future model-weight downloads, matches **any directory named
`models` at any depth**, including `src/sephiroth/models/`. `git add -A`
during the Phase 1 commit silently skipped all seven files. The commit that
landed (`adcd474`) contains only the shim changes that `import` from
`sephiroth.models.*` — the module itself was never committed. `git show
phase-1-model-provider:src/sephiroth/models/gemini.py` confirmed: `fatal: path
... exists on disk, but not in 'phase-1-model-provider'`.

Every verification I ran that session — tests, coverage, eval, two separate
Docker smoke tests — passed, because git leaves ignored/untracked files alone
across branch switches, so the working tree always had the real files. None of
that testing ever touched what was actually *committed*. A teammate cloning
`phase-1-model-provider` fresh would have hit `ModuleNotFoundError` on the
first import.

**Fix**

- Anchored the rule to the repo root (`/models/`) so it can never again match
  a source package by name coincidence.
- Added the seven missing files as a new commit (not an amend — already
  pushed) on `phase-1-model-provider`.
- **Verified with a `git worktree`, not the working directory**: built Docker
  from a detached checkout of the fixed commit alone, confirmed
  `sephiroth.models` imports and the shim identity holds, from a tree that
  contains nothing this session's working directory was carrying along for
  free.

**Decisions**

- **Verifying a commit means testing the commit, not the working tree.**
  Every gate this migration leans on (`pytest`, Docker build, the smoke test)
  was run against `cwd`, which silently included ignored-but-present files.
  Going forward, any "does the committed tree actually work" question gets
  answered from a `git worktree add --detach <ref>`, never from the working
  directory — the working directory is exactly the thing that hid this bug.

**Results**

- `phase-1-model-provider` now builds and imports cleanly from a bare
  worktree checkout; re-verified via Docker.
- Pushed the fix commit; ready to branch Phase 2 from the corrected tip.
