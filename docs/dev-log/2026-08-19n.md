# 2026-08-19 (session 14)

## Session — Phase D: frontend (patient portal, schedule UI, role-aware shell)

**Goal**

Fourth of 5 phases in the landing/icon/portal/scheduling plan. Wire the
three backend phases (A/B/C) into the frontend: a role-aware shell that
shows clinician chrome or patient chrome, a clinician-facing `/schedule`
week grid, and the patient portal pages.

**Did**

- `AuthUser`/`UserOut` gained `role`/`patient_id`; added
  `lib/auth.ts::homeFor(role)` as the single source of truth for where a
  role lands post-login, reused by the login page, the claim page, and
  the auth guard — so those three places can never disagree.
- `components/auth-guard.tsx` — a client-side role gate. No
  `middleware.ts`: the JWT lives in `localStorage`, which Next middleware
  cannot see, so there is nothing server-side to gate on. This also
  incidentally fixes a pre-existing UX rough edge (logged-out users
  briefly seeing dashboard chrome before the 401 bounced them) since the
  guard now renders `null` until the role check completes.
- `lib/routes.ts` centralizes route-to-role classification
  (`isChromelessRoute`/`isClinicianRoute`/`isPatientRoute`) so
  `app-shell.tsx`, the guard, and the sidebar all read from one place.
- Two new primitives that didn't exist anywhere in this codebase yet: a
  `Sheet` (right-side drawer, used for booking/working-hours/sharing) and
  a `Toast` provider (mutation feedback — a 409 double-book has to be
  visible, not silent).
- `/schedule`: a real week grid (7 day columns × 30-minute rows,
  07:00–20:00), appointment cards positioned by minute offset, a working-
  hours sheet, and a booking sheet that shows only server-computed open
  slots as clickable chips — a clinician never gets a free-text time
  input, so the conflict rules built in Phase C are enforced by
  construction on the frontend too, not just trusted server-side.
- Patient portal: `/portal` (health summary + upcoming appointments +
  unread-results count), `/portal/appointments` (list + cancel),
  `/portal/results` (list, unread dot, attachment count),
  `/portal/results/[id]` (detail, clinician message, AI-drafted
  disclosure, attachment downloads), `/portal/claim` (public claim-code
  redemption — no chrome, no auth required to reach it).
- Patient detail page gained an "Invite to portal" button (issues a claim
  code, copies it to the clipboard) and a "Share a result" button opening
  a sheet that lists shareable lab/imaging events.
- Dashboard gained a "Today's agenda" card querying the new
  `GET /api/scheduling/agenda/today`.

**Decisions**

- **No `middleware.ts`, ever, for this token scheme.** Reaffirmed from the
  plan: moving to an `httpOnly` cookie to make middleware possible is a
  real, larger change (CSRF handling, every `authHeaders()` call site,
  CORS credentials config) that stays explicitly out of scope. The client
  guard's job is UX, not the security boundary — every backend route is
  independently authorized regardless of what the frontend shows.
- **Attachment downloads go through `getBlob` + `createObjectURL`, not a
  plain `<a href>`.** Caught this before it shipped: a direct anchor to
  an authenticated download route can't carry the `Authorization` header
  (it lives in localStorage, not a cookie), so it would 401 on click. Same
  pattern the existing PDF export already used — followed it rather than
  inventing a new one.
- **Booking only shows server-computed slots, never a free-text time
  field**, even though the backend would reject an invalid time anyway.
  Redundant-looking, but it means a patient physically cannot construct
  an out-of-hours or already-booked request from the UI, which is a
  better experience than "type a time, then get a 422."

**Tried and rejected**

- Nothing structural — the design from the earlier planning pass (sheet/
  toast primitives, `date-fns` only, client-side guard) held up during
  implementation without revision.

**Problems**

- **No browser automation tool was available in this environment.**
  Could not visually verify the UI in a live browser, which the project's
  own conventions call for on any frontend change. Compensated with: a
  clean `npm run build` (full TypeScript check across all 17 routes,
  including both dynamic routes), and a running dev server + real backend
  with every new route curled for a non-500 status. This is a real,
  stated limitation of this verification pass — the actual click-through
  (register → set hours → book → invite → claim → share → download) has
  not been visually confirmed, only that it compiles and every page
  renders its initial HTML without a server error.
- Caught and fixed one bug via the TypeScript build itself, before it
  became a runtime issue: `StatusPill`'s prop is `label`, not `status` —
  the portal appointments page passed the wrong prop name, and `tsc`
  flagged it immediately.

**Results**

- `npm run build`: clean, all 17 routes (2 dynamic) compile and
  type-check.
- Dev server + real backend (against a real local Postgres) both boot;
  every new route (`/schedule`, `/portal`, `/portal/claim`,
  `/portal/appointments`, `/portal/results`) returns a non-error status.
