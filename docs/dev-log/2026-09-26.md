# 2026-09-26 (session 18)

## Session — Dashboard data trust: impossible blood pressures and duplicate patients (SF068, #132)

**Goal**

Priority 1 from a dashboard review: alerts showed blood pressures no body
produces (653 and 1314 mmHg), and the same patient appeared in several
separate rows of "What you need to do today." If a clinician distrusts one
alert, they distrust all of them. User story: GitHub issue #132.

**Root cause — impossible values**

This was a parsing bug, not missing validation. `synthetic_daily.py` read
the split `bp_systolic`/`bp_diastolic` snapshot keys by keeping only digit
characters, which dropped the decimal point: the Synthea import stores
`"131.4 mm[Hg]"`, and that became `1314`. The job then wrote the bad value
back into the snapshot, inserted it as a critical `LabResult`, and
generated a "Hypertensive range" alert. Because `_next_bp` pulls an
abnormal reading back toward baseline by only 25% a day, the absurd value
stayed for days. The lab path at the top of `_simulate_patient` already
kept `.`, so only blood pressure was affected.

A second gap made it visible: `risk.py` flagged anything ≥160/100 with no
upper bound. Physiological ranges already existed in
`sephiroth.clinical.vitals.VITAL_SPECS` (systolic 40–300, diastolic
20–200), but only encounter vitals used them.

**Root cause — duplicates**

`/dashboard/action-items` returned one row per signal. A single blood
pressure spike could produce an `alert` row, a `deteriorating` row and two
`lab` rows (systolic and diastolic) for the same patient.

**Fix (three code commits, one story id)**

1. Parse with `risk._first_number` (keeps the decimal). If the snapshot
   already holds an implausible reading (written by the old bug), restart
   from baseline instead of drifting back slowly.
2. `is_physiologically_plausible` (`clinical/vitals.py`, aliases the
   snapshot keys to `VITAL_SPECS`). The risk engine raises no BP flag and
   `bp_abnormality` returns `(False, False)` for an implausible reading;
   `/action-items` hides implausible `LabResult` rows on read (no clinical
   record deleted). Data migration `900b7eb6f507` resolves only active
   `risk_engine` "Hypertensive range" alerts whose recorded reading is
   implausible; a plausible alert is never auto-resolved, consistent with
   `alerts.py`'s rule that closing a real alert is a clinician's call.
3. `/action-items` now returns `{groups, total_count}`: one group per
   patient with its worst severity and every signal inside. The dashboard
   renders one card per patient.

**Found along the way**

- The e2e mock never served `/api/dashboard/bootstrap`, so `/dashboard`
  rendered "backend down" in Playwright and the responsive checks passed
  having checked nothing (the exact trap `platform/frontend/CLAUDE.md`
  warns about). Now mocked, with a patient carrying two signals.
- `tests/test_alembic_migration.py` fails locally on drift that predates
  this work (`tasks`, `push_*`, `alerts.rule_key`/`kind`, …). The test's
  docstring says it is tracked in `docs/project-state.yaml`, but no entry
  there covers it — worth its own story. The SF068 migration is data-only
  and was exercised against the local Postgres: it resolved a `1314/653`
  alert and left a `170/105` alert active.

- The local eval gate (`intelligence.evaluation.run --mode ci`) fails on
  `citation_precision` 0.5185 < 0.60 — identical on a clean `origin/main`
  worktree, so it depends on the local RAG corpus, not on this change.
