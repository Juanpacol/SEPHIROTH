# 2026-09-26 (session 18)

## Session — Dashboard data trust: impossible blood pressures and duplicate patients (SF068, #132)

**Goal**

Priority 1 from a dashboard review: alerts showed blood pressures no body
produces (653 and 1314 mmHg), and the same patient appeared in several
separate rows of "What you need to do today." If a clinician distrusts one
alert, they distrust all of them. User story: GitHub issue #132.

**Root cause — impossible values**

This was a parsing bug, not missing validation. `synthetic_daily.py` read
the split `bp_systolic`/`bp_diastolic` snapshot keys by keeping only digit
characters, which dropped the decimal point: the Synthea import stores
`"131.4 mm[Hg]"`, and that became `1314`. The job then wrote the bad value
back into the snapshot, inserted it as a critical `LabResult`, and
generated a "Hypertensive range" alert. Because `_next_bp` pulls an
abnormal reading back toward baseline by only 25% a day, the absurd value
stayed for days. The lab path at the top of `_simulate_patient` already
kept `.`, so only blood pressure was affected.

A second gap made it visible: `risk.py` flagged anything ≥160/100 with no
upper bound. Physiological ranges already existed in
`sephiroth.clinical.vitals.VITAL_SPECS` (systolic 40–300, diastolic
20–200), but only encounter vitals used them.

**Root cause — duplicates**

`/dashboard/action-items` returned one row per signal. A single blood
pressure spike could produce an `alert` row, a `deteriorating` row and two
`lab` rows (systolic and diastolic) for the same patient.

**Fix (three code commits, one story id)**

1. Parse with `risk._first_number` (keeps the decimal). If the snapshot
   already holds an implausible reading (written by the old bug), restart
   from baseline instead of drifting back slowly.
2. `is_physiologically_plausible` (`clinical/vitals.py`, aliases the
   snapshot keys to `VITAL_SPECS`). The risk engine raises no BP flag and
   `bp_abnormality` returns `(False, False)` for an implausible reading;
   `/action-items` hides implausible `LabResult` rows on read (no clinical
   record deleted). Data migration `900b7eb6f507` resolves only active
   `risk_engine` "Hypertensive range" alerts whose recorded reading is
   implausible; a plausible alert is never auto-resolved, consistent with
   `alerts.py`'s rule that closing a real alert is a clinician's call.
3. `/action-items` now returns `{groups, total_count}`: one group per
   patient with its worst severity and every signal inside. The dashboard
   renders one card per patient.

**Found along the way**

- The e2e mock never served `/api/dashboard/bootstrap`, so `/dashboard`
  rendered "backend down" in Playwright and the responsive checks passed
  having checked nothing (the exact trap `platform/frontend/CLAUDE.md`
  warns about). Now mocked, with a patient carrying two signals.
- `tests/test_alembic_migration.py` fails locally on drift that predates
  this work (`tasks`, `push_*`, `alerts.rule_key`/`kind`, …). The test's
  docstring says it is tracked in `docs/project-state.yaml`, but no entry
  there covers it — worth its own story. The SF068 migration is data-only
  and was exercised against the local Postgres: it resolved a `1314/653`
  alert and left a `170/105` alert active.

- The local eval gate (`intelligence.evaluation.run --mode ci`) fails on
  `citation_precision` 0.5185 < 0.60 — identical on a clean `origin/main`
  worktree, so it depends on the local RAG corpus, not on this change.

**Result**

New tests: `test_synthetic_daily.py` (the module had none),
`test_migration_sf068_implausible_bp.py`, plus cases in `test_vitals.py`,
`test_risk_engine.py`, `test_dashboard_endpoints.py` and the
`action-items-list` component test. Dashboard e2e (320px overflow, touch
targets) passes against a page that now actually renders. Full backend
suite: 1323 passed, coverage 88.77%; `ruff`, `docs_check.py` and
`export_contracts.py --check` clean.

## Session — Dashboard functional clarity: readable names, one language, timestamps, score scale (SF069, #134)

**Goal**

Priority 2 of the dashboard review. Clinicians saw raw keys ("Bp_diastolic"),
English pills and risk labels inside a Spanish UI ("High Risk", "Critical",
"Hypertensive range"), no indication of how old a signal was, and a
"max priority score: 3" with no scale.

**Root causes and fixes (four code commits, one story id)**

1. **Raw names.** `friendlyTestName` (`lib/clinical-text.ts`) fell back to
   capitalizing the raw key when `labs.testName.*` had no entry, and the BP
   keys were only in `patientDetail.labResults.key.*`. Added
   `labs.testName.bp/bp_systolic/bp_diastolic`; the fallback now humanizes
   (`some_test` → "Some test") so no key ever shows with underscores.
2. **Mixed language.** `StatusPill` rendered its label verbatim. It now
   translates through `status.<label>` and falls back to the raw label, which
   fixed every call site at once (dashboard, patients, alerts, schedule,
   portal, approvals). Risk-engine labels get a new `riskLabel()` →
   `risk.label.<slug>`, used on the dashboard, `/alerts` and the patient
   detail page. `/alerts` also lost its hardcoded "Patient {id}", raw
   category and raw filter chips, and the top-bar breadcrumb now uses nav
   labels ("Panel", not "dashboard").
3. **Timestamps.** Every `/dashboard/action-items` item carries
   `occurred_at` (naive UTC ISO; `null` for drug interactions, which have no
   moment of their own). `/evolution` entries gained `worsened_at` to feed
   the deteriorating signal. New `lib/relative-time.ts` wraps
   `Intl.RelativeTimeFormat` (no new dependency) and appends `Z` like
   `components/schedule/time.ts`.
4. **Score scale.** `StatCard` gained optional `suffix`/`hint`; the score
   reads "3 of 3" with a "1 low · 2 moderate · 3 high" legend, matching
   `PRIORITY_SCORE` in `safety/priority.py`. The e2e mock used 90/55, off the
   real scale; now 3/2.5.

**Why risk labels are translated client-side**

`alerts.py` de-duplicates open alerts on `(category, title)` and auto-resolves
on the flag label. Translating in `risk.py` would re-open every active alert
under a new title and break auto-resolve, so labels stay English in storage
and are translated on display, falling back to the authored text.

**Follow-up**

Alert and flag `detail` strings still carry English words around their values
("Potassium 6.4 mEq/L (< 3.5)", "BP 170/105"). Translating them properly needs
structured fields from the backend (`rule_code`, `value`, `threshold`) rather
than string parsing — its own story.

**Result**

New frontend tests for `clinical-text` (names and risk labels),
`relative-time`, `StatusPill`, `StatCard`, plus Spanish rendering of
`/alerts` and timestamps in `action-items-list`. Backend asserts
`occurred_at` per category and `worsened_at`. Vitest 135 passed; backend
1323 passed, coverage 88.79%; Playwright responsive/shell suites pass;
screenshots checked in ES and EN at desktop and 320px.

## Session — Dashboard alert explainability via SDD (SF070, SPEC-031, ADR-019, #136)

**How the scope was chosen**

The review's Priority 3 originally asked for sparklines, a distribution
chart, a per-hour load chart and a patient × vital heatmap. Checking each
against the data:
- **Hourly "risk peaks".** Synthetic labs share one cron timestamp, Synthea
  labs are date-only, and alerts are created at boot or cron time, so this
  chart would have been fabricated.
- **7-day sparklines.** They have no history to draw from, because risk is
  computed live.

A second list of CDSS ideas (feedback loop, false-positive rate, confidence
score, recurrence, explainability) was then weighed by "does it improve the
information a clinician gets *today*":
- The feedback and false-positive metrics only mean something with real
  usage.
- A confidence percentage would invent precision for a deterministic rule
  engine.

What shipped is the part that improves information now: *why* a signal
fired, *how* its test has moved, *whether* it is new, plus a visual summary.

**SDD in one PR, with a human gate**

- The spec was drafted and the process paused for approval.
- After approval came xfail tests-first (19 xfail, 6 regression guards
  already green).
- The implementation removed the markers with exact-string edits, not a bulk
  regex, and the `def test_` count (6 + 5) was checked against the
  tests-first commit, per the SF067 incident.
- The spec went to `1.0.0`/`Implemented` with all 9 ACs green.

**Design points worth remembering**

- `LabRule` now declares `code`/`comparator`/`threshold`/`unit` beside its
  predicate. `test_every_lab_rule_declares_the_threshold_its_predicate_uses`
  fires each rule at, and just short of, its declared threshold, so the two
  can never drift.
- Labels and details stay byte-identical. Alert dedupe (`(category, title)`)
  and auto-resolve key on them.
- An alert's factors are recomputed from the patient's *current* flags: the
  dashboard answers "why is this still firing". A flag that stopped firing
  shows no factors rather than stale ones.
- With factors present, the alert row drops its English `detail`, because the
  translated range bar says the same thing. This closes most of the SF069
  follow-up. Alerts without factors still show the authored detail.
- The dataviz validator flagged warning↔success (ΔE 5.7 protan) and low light
  contrast for the fixed status tokens. Since the design system forbids new
  colours, every segment is also iconed, named and counted, with 2px gaps.

**Follow-ups**

- Clinician feedback on alerts plus false-positive rate (needs a persisted
  outcome field).
- Patient × test heatmap.
- A persisted daily risk snapshot for count sparklines.
- Persisting rule identity on alerts (`rule_key` exists in a migration but
  not in the model).

**Result**

- Backend: 1348 passed, coverage 88.85%.
- Vitest: 145 passed.
- Playwright responsive/shell pass.
- Screenshots checked in ES light and EN dark, at desktop and 320px.
- `docs_check.py` reports no SPEC-031 warnings.

## Session — Top-bar controls flush right (SF071, #138)

**Symptom.** The theme toggle, EN/ES, schedule and notification controls sat
in the middle of the top bar instead of at its right edge. On desktop they
spanned x 744–1009 of a 1440px viewport. iPad and phone had the same problem
(the phone's bell floated mid-bar).

**Root cause.** `components/topbar.tsx` is a `justify-between` flex row with
three children, not two. The third was `<div id="mobile-nav">`, which wraps
the mobile drawer. The drawer is a fixed overlay, so the wrapper has zero
width, but flex layout still counted it as an item and parked the controls
halfway between the breadcrumb and that invisible box.

**Fix.** The wrapper now renders as a sibling after `<header>`, inside a
fragment. `aria-controls="mobile-nav"` still resolves, and the drawer opens,
traps focus and closes exactly as before. Ignoring the reindentation the
fragment forced, the change is 7 lines.

**Guard.** A new `e2e/shell.spec.ts` test asserts that the notification
bell's right edge meets the header's content edge on every viewport project,
and that the breadcrumb stays in the left half. It fails on the previous
`topbar.tsx` in all 4 projects and passes with the fix.

**Local review against the real stack.** The backend ran from the branch on
:8000 against a scratch SQLite seeded with the 12 Synthea patients and 5 daily
simulation runs; the frontend ran as a production build on :3200. Checks:
- Desktop, in Chrome with a real login: bell right edge = content edge
  (1417 = 1417), 2 header children, light and dark theme both correct.
- iPhone 14, in Playwright with a real login: 374 = 374; the drawer opens,
  renders solid once its animation settles, and closes on Escape.

**Noted, not fixed here.** On the critical-patients list, an interaction
`top_flag` ("Interaction: A + B") goes through `riskLabel` only. In Spanish it
therefore stays English, unlike `/alerts` and the action items, which parse it
first. It is a small follow-up in the same spirit as SF069's last commit.
