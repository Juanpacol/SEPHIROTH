# 2026-09-20 (session 16)

## Session — Chatbot stall root-caused; agent/eval audit; golden.json trimmed

**Goal**

Diagnose why `/copilot` hung on some queries ("What blood pressure reading
is considered high?") while answering others instantly ("Do warfarin and
ibuprofen interact?"), fix the root cause, audit the surrounding agent
system for related debt, and reduce the eval dataset's redundancy before
re-establishing it as a real gate. This entry documents the eval-dataset
trim specifically — see the phased plan at
`~/.claude/plans/listo-para-esto-quiero-stateful-sifakis.md` (local, not
committed) for the full multi-PR scope this session started.

**Investigation, ruled out in order**

1. Not the backend being down — logs showed `consultation_persisted`
   completing in ~70s.
2. Not missing RAG coverage — `Understanding Blood Pressure Readings`
   exists, is indexed, cosine similarity 0.789 (well above the 0.636 floor).
3. Not the retrieval score — an earlier read of this session compared the
   RRF fusion score (small numbers by construction) against the 0.636
   cosine floor; those are different scales. Recomputed correctly:
   retrieval works.

**Root cause**

The consultation log for the failing query showed `tool_calls=0`: the
`evidence` agent answered from parametric memory instead of calling
`search_clinical_guidelines`, fabricating a citation that Citation Guard
then stripped. The same agent calls the tool correctly on other queries —
this is model tool-calling inconsistency (`qwen3:8b` via local Ollama,
`think=False`), not a corpus or retrieval defect.

**Audit findings that came out of chasing this** (not yet acted on beyond
this session's Fase 0/1 branches — see the plan file for the rest)

- `coordinator` is dead code in every real deployment
  (`enable_single_agent_mode=True` by default, nothing outside tests flips
  it) — ~235 unreachable lines across `planner.py`, `router.py`, and the
  executor's multi-agent branch.
- `laboratory` (zero tools, 38-word prompt) duplicates what
  `src/sephiroth/safety/risk.py` already does deterministically, with no
  test asserting its actual output content.
- `evidence`'s prompt is ~5x `laboratory`'s and ~4.7x `radiology`'s by word
  count, juggling three distinct concerns (citation integrity, tool-call
  budget policy, voice/format) in one block.
- The "is this a guideline question" regex is maintained independently in
  three places (`fast_path.py`, `intent_router.py`, `planner.py`'s
  unconditional default) and has already drifted.
- `AgentCapability.model_hint` exists in the contract
  (`contracts/capability.py:64`) but is read nowhere — a dead seam for
  per-agent model selection.
- The eval harness's CI gate is broken: `deploy.yml` still triggers on a
  `workflows: ["CI"]` reference to a workflow deleted in SF002, so nothing
  in CI actually blocks an eval regression today despite
  `project-state.yaml` recording `eval_blocking: true`.
- The committed eval baseline (`results/latest.json`) was stale: recorded
  2026-08-31 against 88 cases on `qwen2.5:3b-instruct`; the dataset had
  since grown to 101 cases and the real model is `qwen3:8b`.
- `run_full_mode` exercises `EvidenceAgent` directly, bypassing
  `intent_router` entirely — the harness structurally cannot see "the
  agent skipped its tool," which is the exact bug this session chased.

**Did — golden.json trim**

Decided (with the user, after discussion) that the dataset's 101 cases
were more redundant than useful for what we actually need signal on: 92
`golden`/`paraphrase` cases map to only 18 distinct clinical categories
(via each case's `relevant_doc_ids` → the target document's
`metadata.category`), with e.g. 18 cases for `general_health` and 10 each
for `cardiovascular`/`infectious_disease` testing near-duplicate phrasings
of the same guideline.

Kept exactly one representative `golden` case per clinical category (18
cases) — preferring `golden` over `paraphrase` per category since
paraphrase-language robustness is already covered separately by the 5
`LAY_LANGUAGE_CASES` in `tests/test_embeddings_matching.py`, which are
untouched. Also left fully untouched (they calibrate
`retrieval_min_similarity = 0.636`, whose margin is a measured 0.005 on
each side — see `tests/test_embeddings_matching.py:99-101` and `:200-206`):

- All 5 `adversarial-out-of-scope` cases
- All 4 `adversarial-negative` cases

First cut: 101 → 27 (18 kept golden + 9 adversarial). Rebuilding the
embeddings artifact against that 27-case set (required — `build_artifact`
caches golden queries too, and trimming the dataset changes
`corpus_sha256`) broke 4 previously-passing tests in
`tests/test_embeddings_matching.py`: the 5 `LAY_LANGUAGE_CASES` and
`test_compound_query_surfaces_all_relevant_documents`. Root cause: those
tests build their pipeline with `CachedEmbeddingProvider(inner=None)` — no
live fallback — and their literal query strings turned out to be
word-for-word copies of 6 specific `paraphrase` cases
(`otitis-media-kids-antibiotic`, `preeclampsia-aspirin-timing`,
`afib-doac-vs-warfarin`, `aspirin-primary-prevention-elderly`,
`tb-standard-regimen`, `diabetes-hypertension-agent-choice`) that had just
been trimmed out — so their query embeddings were no longer cached, cache
lookup failed, and retrieval silently fell back to keyword-only for those
specific queries. Verified this wasn't embedding non-determinism first
(compared old vs. new artifact vectors for every shared cache key: cosine
similarity 1.0 across the board) before finding the real cause. Added
those 6 cases back.

Net: `intelligence/evaluation/datasets/golden.json` goes from 101 → **33**
cases (18 representative golden + 6 paraphrase backing the
`test_embeddings_matching.py` literal-text tests + 9 adversarial). No
corpus documents were removed — only which questions test them.
`data/embeddings/artifacts/seed_embeddings.json.gz` was regenerated via
`python -m data.embeddings.build_artifact --provider ollama` (must be
`--provider ollama`, not the default `gemini` — the committed artifact is
`nomic-embed-text`). Full suite green (1281 passed, excluding the
pre-existing, unrelated `test_alembic_migration.py` schema-drift failure
that also reproduces on a clean `origin/main` with no local changes).

**Why a dev-log entry and not a SPEC-0NN**

`docs/specs/SPEC-000-spec-process.md` §NG-2 exempts changes that alter no
contract in an existing spec's §6 — this trim touches no `SPEC-003` type
and no frozen SSE/persistence contract. `SPEC-029` (the next free number;
`SPEC-009`–`SPEC-028` were already allocated and deleted, and specs are
never renumbered) stays reserved for the actual contract change identified
in the audit above: consolidating/removing `coordinator` and `laboratory`,
which does require a spec + a superseding ADR for ADR-004.

**A late finding while wiring this up:** the first working version of the CI
`eval` job accidentally computed `citation_precision` against a stale
`transcripts_sha256` (recorded before 60 orphaned transcript files — for
cases the trim had just removed — were deleted), which coincidentally
diluted the metric to a passing 0.72. Once the hash was corrected to match
the actual 33-transcript directory, the honest replayed number is
**0.5185**, below the 0.60 threshold — matching the raw per-case count from
the `--record` run (13 of 27 citations fabricated) rather than
contradicting it. `main` is branch-protected on `code-review-gate`, so
wiring `eval` in as a blocking check right now would make this PR
unmergeable over a problem it did not introduce and this PR's own scope
(restore the gate's plumbing) isn't meant to fix. Made it **advisory**
instead — `continue-on-error: true`, excluded from `code-review-gate`'s
`needs` — the exact same pattern already established for `type-check`
(mypy) in this workflow for the same reason (DEBT-012). Promote it to
blocking in the Fase 2 PR once the tool-calling reliability fix
(temperature=0 on the specialist's chat call, detecting a
`require_tool_call` violation post-hoc) brings the number back up.
