# 2026-08-19 (session 13)

## Session — Phase C: scheduling + exam-results backend

**Goal**

Third of 5 phases in the landing/icon/portal/scheduling plan. Adds
clinician working hours, computed appointment slots, booking with
server-side conflict rules, and exam-result sharing referencing the
existing timeline rather than a new "lab result" entity.

**Did**

- 5 new models: `AvailabilityRule` (wall-clock + IANA timezone, recurring
  weekly), `AvailabilityException` (UTC-instant one-off block/open),
  `Appointment` (clinician+patient, composite indexes, soft-cancel only),
  `ResultShare` (references `TimelineEvent`, `Integer` FK — the one FK in
  this file that isn't `String(36)`), `ResultAttachment` (`LargeBinary`,
  `deferred=True`, sha256, size/count caps enforced at the API layer).
- `platform/api/scheduling.py::expand_slots` — pure function, no DB, no
  I/O. Wrote ~20 unit tests first, including two DST transitions
  (2026-03-08 spring-forward, 2026-11-01 fall-back), and caught my own
  bug during that process: naive-arithmetic-then-localize is correct,
  but "add a timedelta to an already zoneinfo-aware datetime" silently
  produces wrong UTC instants across a transition (zoneinfo doesn't
  renormalize on `+`). Rewrote `_chunk` to localize each boundary
  independently from a naive wall-clock value instead. Also had to
  correct my own test *expectations* for what "correct" DST behavior even
  means here — the honest answer for an MVP scheduler is "one slot per
  configured step, not adjusted for the missing/repeated real hour,"
  documented as a known limitation rather than chased further.
- `platform/core/storage.py` — a one-method `BlobStore` Protocol so a
  later S3 move is a new class, not a router rewrite.
- New routers `scheduling.py` and `results.py`, wired in `main.py` with
  no blanket router guard (unlike the clinician-only routers from Phases
  A/B) — every handler scopes reads to the caller's own role identity
  (`user.id` for a clinician, `user.patient_id` for a patient), same
  isolation discipline as `portal.py`.
- Migration `08a4a2ef03ab` — generated against a real local Postgres,
  applied/downgraded/re-applied to confirm both directions. Autogenerate
  got everything right this cycle (check constraints via the
  `checkconstraint_byname` plugin, cascade delete, server defaults,
  unique constraints) — zero hand-fixes needed, unlike Phase B's FK
  naming issue.
- Wrote the appointment API test suite (conflict rules, adjacency
  non-overlap, past/horizon rejection, force-bypass, ownership) and it
  immediately caught a real bug (see below) before this ever reached
  Docker verification.

**Decisions**

- **A shared result is a `TimelineEvent`, not a new entity.** Sharing
  needs identity, a date, and a narrative — exactly what `TimelineEvent`
  already has and `Patient.lab_results`'s denormalized JSON blob
  structurally cannot. `ResultShare` carries only what's genuinely new
  about the *act* of sharing.
- **No DB-level exclusion constraint against double-booking.** Postgres's
  `EXCLUDE USING gist` has no SQLite equivalent and would break the test
  fixture. Mitigated with a transactional check-then-insert instead;
  documented residual race risk at demo scale.
- **`response_model=` for availability/slots, hand-built dicts for
  appointments.** A clinician sees `notes` on their own appointments, a
  patient never does — a `for_patient: bool` flag on one helper is less
  ceremony than two Pydantic models for the same shape.

**Tried and rejected**

- My first attempt at DST-correct slot chunking (add a `timedelta` to an
  aware zoneinfo datetime) looked reasonable and even passed a
  non-transition test, but produced a degenerate zero-length slot
  (`07:00→07:00`) on the actual transition day — caught by running the
  DST test, not by inspection. Rewrote to localize each boundary
  independently from naive wall-clock arithmetic.

**Problems**

- **Real bug, caught by the appointment test suite itself, before Docker
  verification**: `POST /api/scheduling/appointments` returned 422
  ("outside working hours") instead of 409 ("conflict") when the target
  slot was already booked — `expand_slots` was called with existing
  appointments included for the *working-hours* membership check, which
  subtracts booked slots from the candidate set, making an already-booked
  slot look like it was never open at all. Fixed by checking working-
  hours membership against rules/exceptions only, independent of booking
  status; the separate, explicit conflict queries are what correctly
  produce the 409.
- Two test dates (`2026-01-05`) were in the *past* relative to this
  session's actual system clock (2026-08-17) — every booking test 422'd
  on the past-date check until I picked a genuinely future Monday
  (2026-08-24). A reminder that "looks like a reasonable test date"
  isn't the same as "is actually in the future right now."
