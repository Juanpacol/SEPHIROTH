# 2026-09-27 (session 19)

## Session — De-cluttering the dashboard: "what dominates today" + details on demand (SF072, SPEC-031 1.1.0, #140)

**Goal**

The dashboard felt overloaded, and the user asked whether a chart could help.
It could, but only by *replacing* text rather than adding to it. Two causes of
overload:
1. **Duplicated information.** The critical-patients card listed the same
   patients that already appear as cards in the action list.
2. **Detail always on.** Since SF070 every signal always showed its range
   bar, trend, explanation and recurrence chip.

**Decision (SDD amendment, human gate between Draft and tests)**

- **SPEC-031 1.0.0 → 1.1.0, additive.** New `GET /api/dashboard/rule-summary`
  returns patients per active rule, counted over the same population as
  `/stats`, with all drug interactions in one bucket.
  - The counts had to be exact. Deriving them from `/action-items` would
    undercount, because that list is capped at 8 per category.
  - The user chose to have a bar expand into its patients rather than filter
    the action list (NG-7), for the same cap reason.
- **Frontend.** `RuleSummaryChart` replaces the critical-patients card, and
  `critical-patients-list.tsx` is deleted because it had no other consumer.
  Signal details collapse behind a full-width row toggle, with the first
  explainable signal of each critical group open.
  - The full width meets the repo's "44px in one dimension" rule without
    doubling row height.
  - The first-open rule keeps the urgent "why" visible.

**Real-data check (read-only, against Supabase)**

`_dashboard_rule_summary` and `_dashboard_stats` agree on the real data:
- 32 patients in total;
- 30 with at least one problem, equal to critical (17) + moderate (13);
- `count == len(patients)` for every rule.

The chart also surfaces something the old card hid: **drug interactions
affect 21 of 32 patients**, far ahead of any lab rule.

**Flaky test, root-caused**

`shell.spec.ts` "page content is readable under the tab bar" had been flaky
since before this story. This change made it fail most of the time, for two
reasons:
1. The chart loads on its own query, so the page grows *after* the test's
   single scroll.
2. A smooth scroll restarted inside the poll can stall a pixel short of the
   end.

A settled probe measured the real overlap at 0.5–1 px, which is within
tolerance. The test now scrolls with `behavior: "instant"` inside its poll:
40/40 isolated runs pass and the full suite passes. The assertion's tolerance
did not change.

**Follow-up (not fixed here)**

`_dashboard_stats`' `top_flag` uses `max(flags, key=0 if high else 1)`, which
picks a *medium* flag over a *high* one. The dashboard no longer renders
`top_flag`, but `/stats` still returns it. The fix is to key the max on
severity rank.
